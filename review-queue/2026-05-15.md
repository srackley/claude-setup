### DISPUTED (1 — requires human verification before merge)

**[eks-deploy.yaml + test.yml / paths-ignore on pull_request trigger]**

Adding `paths-ignore` to workflows that are required status checks will leave doc-only PRs permanently unmergeable. GitHub documents this explicitly:

> "If a workflow is skipped due to path filtering… checks will remain in a 'Pending' state. A pull request that requires those checks to be successful will be blocked from merging."

(Source: GitHub Troubleshooting Required Status Checks docs — still an open acknowledged gap as of Dec 2025, with no GitHub-side fix shipped.)

**Challenger verdict: Weakened.** Mitigating evidence found:
- `test.yml` uses `continue-on-error: true` on its only PR-specific step (coverage comment) — not the profile of a hard required check.
- `eks-deploy.yaml` is a deployment pipeline, not a test gate — unusual choice for a required status check.
- No `.github/` artifacts confirm these are required checks.

**What to verify before merge:** Ask scottpcipriano to confirm neither `Test` nor `EKS Build/Deploy` is a required status check in main's branch protection. If either is, the fix is a companion passthrough workflow with the same check name that runs on the inverse path filter and immediately exits success.

---

### Dropped Findings (Refuted by challengers)

1. **post-deploy-test.yaml workflow_run chain** — `post-deploy-test.yaml` handles the missing-artifact case with `should_test=false` and gracefully skips. Skipping E2E tests on a doc-only PR (which never deploys) is correct by design.

2. **No inline comment on .gitignore paths-ignore entry** — `.gitignore` is self-evident in context. Adding a comment would explain the "what" not the "why", contradicting the repo's CLAUDE.md commenting philosophy.

### False Positives

- `.gitignore` scope issue — only one `.gitignore` exists in the repo (root only). Pattern is complete.
- Missing `branches: [main]` on `eks-deploy.yaml` — pre-existing asymmetry, not introduced by this PR.

---

### Verdict

One disputed finding requiring branch protection verification. No blocking or suggestion-level findings survived challenge. The change itself is correct and well-reasoned.

## wanderu/ui-react#960 — fix: c2c page crash on missing locationData (departure/arrival)

**URL:** https://github.com/wanderu/ui-react/pull/960  
**Author:** scottpcipriano  
**Classification:** NEEDS_REVIEW  
**Status:** Reviewed 2026-05-15

---

### Summary

Guards `getPSearchParams` against missing `.departure`/`.arrival` sub-fields, adds early-return thunk guards with structured warning logs, and adds unit tests for the new guard branches. Addresses a recurring Datadog RUM issue (162 errors, 24 sessions/7d) on city-to-city pages where WAPI returns incomplete `locationData` (canonical reproducer: Yosemite→Santa Barbara train — no train station at Yosemite).

bsaltersheridan2 left a prior comment with 4 nit-level observations (UTC vs spec §5, plan/code drift, downstream broken-UI follow-up, operational follow-ups). No blocking findings from that reviewer.

---

### Findings

**BLOCKING:** None.

**SUGGESTIONS (2):**

**S1 — No thunk tests for the new guard paths in `fetchCachedTrips`, `fetchAllTrips`, `fetchTimeTableData`**  
`packages/wanderu-app-seo/src/ducks/actions/fetchCityToCityData/index.js`

There is no test file for `fetchCityToCityData/index.js` anywhere in the package. Both container test files that import symbols from this module mock it entirely at the top level, so the thunk bodies — including the `if (!psearchParams) { return; }` guards and the `i18nMoment.utc()` fallback — are never executed by any test.

CLAUDE.md's TDD mandate is unambiguous. The PR body acknowledges this gap ("cost was higher than the value for this PR") without deferring to a tracked ticket. Concrete regression scenario: a future refactor that drops the null check would cause `fetchCachedTripsAction.fetch` to be called with undefined params on SSR requests with no test catching it.

**S2 — `MultiModalCityToCity.jsx` test mock prevents the `|| {}` fallback from ever being exercised**  
`packages/wanderu-app-seo/src/containers/MultiModalCityToCity/tests/MultiModalCityToCity.test.jsx`

The mock at line 6 (`jest.fn(() => ({}))`) hardwires `getPSearchParams` to `{}`, so the `|| {}` fallback is never triggered. Only one `mapStateToProps` test case exists (boston→new-york happy path). The mock also violates the repo's "Minimal mocking" convention — using the real `getPSearchParams` with an incomplete `locationData` fixture would naturally exercise the fallback without a mock.

---

### DISPUTED (2 — requires human verification before merge)

**D1 — `|| {}` fallback in `MultiModalCityToCity.jsx` is a fragile design**

Three agents independently identified that `{}` serializes to the degenerate key `"--"` in `serializeSearchParams`, causing `isFetchingAllTrips = true` permanently and dispatching `fetchAllTrips({})` with all-undefined fields — a malformed API call.

**Challenger verdict: Weakened.** No data entry in `modeData.js` or `modeDataTest.js` has `showTrips: true` co-occurring with incomplete `locationData`. The triggering condition doesn't exist today. Residual risk: if a future data entry adds that combination, the fallback silently produces an infinite spinner plus spurious `psearch.json` call with no guard.

**What to verify before merge:** Confirm whether `showTrips: true` + incomplete `locationData` is possible by design. If not, add a code comment documenting that invariant. If it is possible, replace `|| {}` with a real guard in the `useEffect`.

**D2 — `CityToCity.jsx` (classic C2C container) is an uncovered caller**

`CityToCity.jsx:370` calls `getPSearchParams` and passes the result to selectors without guarding `undefined`. After this PR, `undefined` is returned for more inputs, so routes with incomplete `locationData` would now produce `isFetchingAllTrips = true` permanently (infinite spinner) instead of a TypeError crash.

**Challenger verdict: Weakened.** Pre-PR code crashed on this path anyway via a different mechanism. This is a symptom change (crash → spinner), arguably better UX. Also unclear whether Yosemite→Santa Barbara train actually routes through `CityToCity.jsx` vs `MultiModalCityToCity.jsx`.

**What to verify before merge:** Confirm which container handles `/en-us/train/us-ca/yosemite-national-park/us-ca/santa-barbara/`. If `CityToCity.jsx` handles it, add the same `if (!psearchParams)` guard there.

---

### False Positives

- `i18nMoment.utc()` validity — confirmed valid (moment-timezone inherits `.utc()` from moment core)
- Pre-existing broad catch blocks swallowing errors — pre-existing behavior, not introduced by this PR

---

### Verdict

Two disputed findings requiring human verification. Two suggestions (thunk test coverage, container mock improvement). No blocking findings survived challenge. The core fix is correct and well-structured.
