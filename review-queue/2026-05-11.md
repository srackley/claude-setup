## wanderu/canopy #543 — docs(ticket-lookup): always show API delivery instructions; add escape hatch for ETICKET/PRINT_OUT noticket

**URL:** https://github.com/wanderu/canopy/pull/543
**Classification:** NEEDS_REVIEW

### What it does
Spec-only update to `.docs/specs/ticket-lookup/frontend-design.md` for a v1.1 iteration of the ticket-action area. Rolls status back to IN PROGRESS. Core rule: always show API delivery instructions per `deliveryInstructions.type` regardless of `ticket.status`, then layer additional UI on top. Drops the dedicated processing UI (falls through to noticket). Adds escape hatch for `noticket + ETICKET/PRINT_OUT`. Updates FR-9, §2 user stories, §7 ACs, §8 risks, §9 out-of-scope, §10 architecture/component description.

### Prior review
srackley left 3 unresolved items on the current head commit: (Thread 1) concern that "always show" instructions is wrong for `available + WILL_CALL/CONFIRMATION_NUMBER`; (Thread 2) prefers instructions-first layout over button-first; (review comment) `processing_shown` still in Amplitude table.

---

### BLOCKING

**B1: "Always show instructions" unresolved for `available + CONFIRMATION_NUMBER / MANIFEST / WILL_CALL` — and the type system confirms the gap**
File: `.docs/specs/ticket-lookup/frontend-design.md`, lines 57–66 (FR-9); also `src/entities/trip/types.ts` line 39

The "always show" rule produces contradictory UI for `available + WILL_CALL` or `available + CONFIRMATION_NUMBER`: a "Download Ticket" button next to "Pick up your tickets at the station" is self-contradictory. The existing type confirms this is uncharted territory: `TicketInfo.available` in `types.ts` is `{ status: 'available' }` with no `deliveryInstructions` field at all — v1.1 requires adding it, but the spec never calls out the required type change, nor does it address what to render for the contradictory combinations.

The spec needs to either (a) carve out an exception — only show delivery instructions for `available + ETICKET/PRINT_OUT` (where the instructions tell the user what to do with the ticket they're downloading), or (b) explicitly acknowledge and resolve the `available + WILL_CALL/CONFIRMATION_NUMBER/MANIFEST` combination. It also needs to note the required type change to `TicketInfo.available`.

*Confirms and extends Thread 1.*

**B2: `processing_shown` still in §6 Amplitude events table**
File: `.docs/specs/ticket-lookup/frontend-design.md`, line 170

`processing_shown` is still listed as a valid `interaction_type` for `Ticket Lookup Interacted`. FR-9, §7, and §8 all confirm the dedicated processing UI is gone — `processing` falls through silently to noticket. There is no UI state in v1.1 that fires `processing_shown`. Remove it. §7 and §8 are already consistent with removal.

*Confirms the separate review comment.*

---

### SUGGESTIONS

**S1: `Ticket Lookup CS Clicked` missing `location` values for escape hatch and not-found banner**
File: `.docs/specs/ticket-lookup/frontend-design.md`, line 172

The event table lists only `location (form)`. The v1.1 spec adds CS links in the `noticket + ETICKET/PRINT_OUT` escape-hatch sub-block (FR-9 line 67) and the not-found error banner (FR-11 line 76). §8 line 241 explicitly requires tracking `Ticket Lookup CS Clicked` segmented by carrier in the `noticket` state — that segmentation is impossible if all CS clicks emit `location: 'form'`. Suggested expansion: `location (form, not_found_banner, escape_hatch)`.

**S2: Thread 2 (instructions-first layout) still open in the spec**
File: `.docs/specs/ticket-lookup/frontend-design.md`, line 66 and wireframe at line 338

FR-9 line 66 still reads "The order in the UI is button-then-instructions." Thread 2 is unresolved. Worth settling before implementation starts.

---

### NITS

**N1: `carrierName` null/empty fallback not specified for the escape hatch**
File: `.docs/specs/ticket-lookup/frontend-design.md`, line 67

The escape hatch renders `carrierName` as plain text. `TripLeg.carrier.name` is typed `string` (non-nullable), which provides structural protection at the entity level. However, the spec doesn't say how the BFF should handle a missing carrier name from wtix, or what copy `TicketAction` renders for an empty string. Suggest one line: "If `carrierName` is empty or unavailable, omit the third escape-hatch option or render 'the carrier's website' as fallback copy."
