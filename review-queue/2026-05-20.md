#### SUGGESTION (1)

**TicketLookupForm.test.tsx:~248 — Catch-path test doesn't verify the terminal `.error()` call**

The "shows inline error when findBooking throws unexpectedly" test asserts `mockWithMetadata` was called with `{ outcome: 'server_error' }`. But the catch block calls `.withError(error).withMetadata({ outcome: 'server_error' }).error('Ticket lookup failed unexpectedly')`, and the terminal `.error(...)` fires on an anonymous untracked `vi.fn()` from `beforeEach`'s `mockReturnValue`. Every `.info()` call in the component chains off `.withMetadata(...)`, which returns `{ info: mockInfo }` from `beforeEach`. `chained.info` is never reached and can be removed.

**TicketLookupForm.tsx:22 — LOGGER_CONTEXT comment ambiguous on causal chain**

> "an inline literal would re-fire effects depending on `logger`"

The actual chain is: new `context` reference → `useMemo([logger, context])` recomputes → new `Logger` instance → `useEffect([logger, result])` re-fires. The word `logger` is ambiguous between the `useObservability` logger and the `useLogger` return value.

Suggested: _"An inline literal creates a new object each render, causing useLogger's useMemo to return a new Logger instance and re-fire effects on [logger]."_

## wanderu/ui-react #960 — fix: c2c page crash on missing locationData (departure/arrival)

**Branch:** fix/citytocity-departure-undefined  
**Head SHA:** b1b960ab0597bdc30729631337e277a39e3af930  
**Classification:** NEEDS_REVIEW  
**Review action:** REQUEST_CHANGES (1 blocking finding)  
**URL:** https://github.com/wanderu/ui-react/pull/960  

### Context

Guards `getPSearchParams`, `fetchCachedTrips`, `fetchAllTrips`, and `fetchTimeTableData` in `wanderu-app-seo` against missing `locationData.departure`/`locationData.arrival`. Fixes a recurring TypeError (Datadog issue `a86a9da4`) on c2c SEO pages since 2024-07. 8 files, +353/-4 (bulk is spec/plan/CLAUDE.md docs). Prior reviewer bsaltersheridan2 (COMMENTED, no blocking findings).

### Findings

#### BLOCKING (1)

**`MultiModalCityToCity.jsx:205–207` + `35–43` — `|| {}` fallback replaces crash with repeated degenerate API calls**

When `locationData.departure`/`.arrival` is missing and `showTrips` is `true`, `getPSearchParams` returns `undefined` and the `|| {}` fallback produces a brand-new `{}` object on every `mapStateToProps` call. Each new reference fails `Object.is` comparison in the `useEffect` deps, so `fetchAllTrips({})` fires on every Redux-triggered re-render. `fetchAllTripsAction.fetch` checks `working || success` but not `error`, so after an API failure the guard doesn't block subsequent calls. Any unrelated Redux dispatch (locale change, split-test selector) causes another degenerate psearch request with `undefined` place IDs. Additionally, `serializeSearchParams({})` produces `"undefined-undefined-undefined"` as the cache key, causing `isFetchingAllTrips` to be stuck `true` until the first error clears it — showing an infinite loading spinner.

Fix: keep `psearchParams` as `undefined` (not `{}`) when `getPSearchParams` returns falsy, and guard the selectors and `useEffect`:

```js
const psearchParams = data?.locationData
    ? getPSearchParams(data.locationData, departDate)
    : undefined;

// useEffect
if (data?.showTrips && psearchParams?.originPlaceId) {
    fetchAllTrips(psearchParams);
}
```

Verify `selectWorking(state, undefined)` / `selectSuccess(state, undefined)` fall back safely in `serializeSearchParams` (returns `undefined` → `baseState` lookup miss, not a crash).

#### SUGGESTION (1)

**`fetchCityToCityData/index.js:37–43` — The exact crash path has no regression test**

The timezone optional-chaining (`locationData?.departure?.timezone`) — the precise line that caused the production crash — has no unit test. The entire `fetchCityToCityData` module is wholesale-mocked in all container tests; none of its thunk logic is exercised. If the `?.` were removed in a future merge conflict, no test would fail before the crash reappears. Given CLAUDE.md's TDD mandate and the fact this was a production crash fix, a thunk test confirming `fetchTimeTableData` survives `locationData = null` or missing departure is the single highest-value test this PR could add. The PR description already notes this as a Medium follow-up — worth filing as a tracked issue.

#### DISPUTED NIT (1)

*Weakened by challenger — real but overstated.*

**Plan doc / implementation divergence — wall-clock vs UTC fallback**

The plan at `.docs/plans/citytocity-departure-undefined/2026-05-11-fix.md` specifies `i18nMoment()` (wall-clock) as the timezone fallback with the rationale "better to use the client's wall clock than to crash." The implementation uses `i18nMoment.utc()`. The spec §3.3 accommodates either choice ("UTC or no timezone shift"), so the implementation is correct. The plan is just stale. A one-line plan update noting the UTC choice and rationale would remove ambiguity for future readers. Not blocking.
