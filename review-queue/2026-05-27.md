## wanderu/canopy#597 — build(deps-dev): bump the commitlint group across 1 directory with 2 updates

**URL:** https://github.com/wanderu/canopy/pull/597
**Classification:** NEEDS_REVIEW
**Reviewed:** 2026-05-27
**Agents:** code-reviewer, silent-failure-hunter, type-design-analyzer, pr-test-analyzer, comment-analyzer

### Summary

Dependabot PR bumping `@commitlint/cli` and `@commitlint/config-conventional` from `^20.5.3` to `^21.0.1` — a **major** version bump (v20 → v21). Only `package.json` and `pnpm-lock.yaml` changed.

**v21.0.0 breaking changes (from PR body):**
- Minimum Node version: `>=22.12.0` (was `>=v18`). Canopy uses Node 24.3.0 (`.tool-versions`) — safe.
- Output format change: `feat!: show input from a new line` — cosmetic only; `--legacy-output` flag added for backwards compat. No downstream tooling in this repo parses commitlint output.
- Dependency replacements: dropped `minimist`, `import-meta-resolve`; replaced `lodash.mergewith` and `lodash.merge` with `es-toolkit`.

Commitlint is used **only** as a local husky git hook (`pnpm dlx commitlint --edit $1` in `.husky/commit-msg`) — not in CI. Post-deploy tests passed on dev. CI has zero commitlint coverage. Auto-merge is correctly blocked for semver-major (confirmed in `dependabot-auto-merge.yaml`).

### Findings

#### VALID — nit (challenger: Confirmed)

**Stale version reference in parserPreset workaround comment**
`commitlint.config.mjs` ~line 19-20

The comment reads "Verified at `@commitlint/load@20.5.0`" but:
1. The PR installs `@commitlint/load@21.0.1`.
2. The actual pre-PR installed version was `20.2.0` (not `20.5.0` as the comment claimed — already stale before this PR).

The version marker's purpose is to signal when re-verification is needed. A major version bump (v20 → v21) that swaps `lodash.mergewith` for `es-toolkit.mergeWith` in `resolve-extends` is exactly the kind of change the workaround's correctness depends on.

**Suggested comment update:**
```js
// Verified at @commitlint/load@21.0.1. The workaround relies on @commitlint/resolve-extends
// merging the extends chain's parserPreset string with this object — with the user object winning
// on type mismatch. v21 replaces lodash.mergewith with es-toolkit.mergeWith for this merge;
// re-verify feat!: syntax and issuePrefixes:[] behavior if upgrading further.
```

#### DISPUTED — suggestion (challenger: Weakened)

**`.husky/commit-msg` uses `pnpm dlx` instead of `pnpm exec`**
`.husky/commit-msg:1`

`pnpm dlx commitlint --edit $1` downloads the package from the npm registry in an isolated ephemeral environment, bypassing `node_modules`. The conventional pattern for Husky hooks is `pnpm exec commitlint --edit $1` — uses `node_modules/.bin`, works offline, consistent with how ESLint/Prettier are invoked via `task` scripts.

**Challenger (Weakened):** The version-mismatch risk is overstated: since `package.json` pins `"^21.0.1"` (caret range), `pnpm install` already permits 21.x drift, so `pnpm dlx` and `pnpm exec` expose the same version surface. The stronger arguments are consistency and offline reliability. Weakened from suggestion to disputed.

**Suggested fix (still worth doing):**
```
pnpm exec commitlint --edit $1
```

#### UNCERTAIN — suggestion

**es-toolkit replaces lodash.mergewith — parserPreset workaround needs manual re-verification**
`commitlint.config.mjs` (full file)

The custom parserPreset workaround in `commitlint.config.mjs` was written specifically because `@commitlint/resolve-extends@20.x` used `lodash.mergewith`, which "lets the user object win when types mismatch." In v21, this is replaced by `es-toolkit.mergeWith`. `es-toolkit` is designed to be lodash-compatible, but specific type-mismatch merge semantics are not directly verifiable without running the code.

The failure mode if the behavior changed: `issuePrefixes: []` not applied (body lines with `#N` misclassified as footer tokens), OR `feat!:` syntax rejected (`subject-empty`/`type-empty` errors).

**Manual test recommended before merging:**
```bash
# After task install with v21:
git commit --allow-empty -m "feat!: test breaking change"
# Must exit 0

git commit --allow-empty -m "fix: something" -m "Fixes issue #42 in the body
Another body line"
# Must exit 0 (issuePrefixes:[] should prevent #42 from triggering footer-leading-blank)
```

- No `engines` field in `package.json` — pre-existing; canopy relies on `.tool-versions`.

- `conventional-changelog-conventionalcommits` unchanged at 9.3.1 — the "re-diff" note in `commitlint.config.mjs` is NOT triggered by this PR.

### Verdict

**Blocking:** none

**Uncertain:** 1 (es-toolkit merge semantics — manual testing recommended before merge)

Safe to merge, but reviewer should: (1) update the version comment, and (2) manually run the two `git commit --allow-empty` tests to confirm the parserPreset workaround still holds in v21.
