### Summary

Bumps `@amplitude/analytics-browser` from `^2.22.0` to `^2.38.1` (resolved to `2.42.3`). **Production code is correct and safe.** `cookieOptions.domain` is the right SDK v2.x API key. `domain: undefined` is handled gracefully by the SDK (triggers auto-TLD detection). No new silent failure modes.

### Findings

#### DISPUTED — suggestion (challenger: Weakened)

**Test: value-passing contract not asserted**
`packages/wanderu-analytics/src/tests/AmplitudeProvider.test.tsx`

The two assertions check key presence only — `toHaveProperty('domain')` passes when `domain` is `undefined` (which it always is in the test environment). A regression where the production code reads from a misspelled config path would not be caught. The `setConfig` mock utility is available and could be used to inject a real domain value and assert it flows through.

**Challenger (Weakened):** `serverUrl` is also never tested with a real value — the same pattern is consistent across the existing suite. The test does catch the most likely regression (top-level vs `cookieOptions.domain` nesting). Weakened, not refuted.

#### VALID — nit (challenger: Confirmed)

**Misleading "legacy" comment**
`packages/wanderu-analytics/src/tests/AmplitudeProvider.test.tsx`

The inline comment says "not the legacy top-level `cookieDomain`" — implying there was a prior top-level `cookieDomain` call in this codebase. There was not; `AmplitudeProvider.tsx` had no cookie domain configuration before this PR. The "legacy" framing describes the external SDK's v1.x API, not a removed pattern in this file.

**Suggested wording:**
```
// The contract being verified: the SDK v2.x option key is `cookieOptions.domain`
// (the v1.x SDK accepted a top-level `cookieDomain` — this file uses the v2.x shape).
```

#### UNCERTAIN — suggestion

`package.json` + `yarn.lock`

Bumped `@amplitude/analytics-browser` `^2.22.0` → `^2.38.1`, resolved to `2.42.3`. PR description says "Reviewers: please diff the changelog" but doesn't include findings. Also notes the resolved version is `2.42.3` while the PR description says `2.41.0` — minor discrepancy. Worth confirming changelog was checked before merging.

### Findings

#### Pre-existing nit (outside PR diff — not blocking merge)

**Inaccurate comment explaining absolute URL requirement**
`src/test-utils/msw/handlers/wapi.ts:4-5`

The JSDoc comment says "MSW 2.13+ passes glob/RegExp through path-to-regexp v8 which rejects wildcard patterns." This is factually wrong: the lockfile stanza for `msw@2.14.6` lists `path-to-regexp: 6.3.0` as its dependency. path-to-regexp@8.4.2 is present in the lockfile but belongs to `nise@6.1.1` (sinon), not msw. The real reason absolute URLs are required is that jsdom's `fetch` emits absolute URLs, so handler patterns must be absolute to match — a property of the test environment, not a path-to-regexp version change.

**Challenger verdict:** Confirmed — "The comment invents a false causal chain."

**Suggested correction:**
```
/**
 * MSW endpoint patterns. Absolute URLs required — in jsdom, `fetch` emits absolute
 * URLs, so handler patterns must be absolute to match. Keep in sync with the
 * getServerEnv() mock (wapi.baseUrl: 'http://test.wapi.local') in any test that
 * uses this handler.
 */
```

Pre-existing (not introduced by this PR). Safe to fix in a follow-up or the next PR that touches this file.
