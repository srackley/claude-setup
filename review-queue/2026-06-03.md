### Disputed (1)

**`carriers.js:35-45` — Missing `/ tripSeats` normalization for stale multi-pax totals**  
`paxAwarePricing` multiplies `trip.pricing` directly by `requestedSeats` when `tripSeats !== requestedSeats`. For a stale 2-pax Amtrak trip (`trip.seats='2'`, `trip.pricing=$200`) in a 3-pax search, this produces `$200 × 3 = $600` instead of `($200/2) × 3 = $300`. The canonical `selectTripPrices` in `wanderu-ducks-trips/selectors.js:301-360` handles this with `normalizedSeats = tripSeats > 1 ? tripSeats : 1`. The stale scenario is confirmed reachable: `serializeSearchParams` excludes `seats` from the search key. Challenger weakened to DISPUTED — exposure is transient (sidebar only, until next JIT scrape completes, not a booking-path bug).

### Nits (1)

**`carriers.js:60` + comment `19-27` — NaN path undocumented, diverges from M1**  
`Number.parseInt(trip.seats, 10)` returns `NaN` when `trip.seats` is absent. `NaN === seats` is always false, so multiply always fires — correct behavior, but undocumented. M1's equivalent at `wanderu-ducks-trips/selectors.js:298-302` has an explicit comment. A future maintainer adding `if (!isNaN(tripSeats))` would silently break single-pax cached trip handling. Challenger: Confirmed.

## wanderu/ui-react #896 — fix: per-env Amplitude cookieDomain via cookieOptions.domain (#873)

**Author:** bsaltersheridan2  
**Classification:** NEEDS_REVIEW  
**Review action:** COMMENT  

### Blocking
None.

### Suggestions (1)

**`AmplitudeProvider.test.tsx:869–870` — Test verifies key existence, not value; fix can be silently reverted**  
The new test asserts `toHaveProperty('cookieOptions')` and `toHaveProperty('domain')` — both of which pass when the value is `undefined`. The test comment acknowledges this: "appconfig in tests doesn't set cookieDomain, so `domain` is undefined." Jest's `toHaveProperty('key')` checks key presence, not value. The production code always spreads `cookieOptions: { domain: appSettings?.config?.amplitude?.cookieDomain }`, so `domain` is always present in the object. If a future refactor removes config-sourcing but keeps `cookieOptions: { domain: undefined }`, the test still passes. No companion test exists with a real `cookieDomain` value verifying end-to-end flow from config to the SDK init call — the stated purpose of the PR (fixing cross-app device ID continuity) is not regression-protected. Challenger: Confirmed. Fix: add a second test that uses `setConfig` (or `ssrHydratedState({ cookieDomain: '.wanderu.com' })`) to inject a known value and assert `expect(initOptions.cookieOptions?.domain).toBe('.wanderu.com')`.

### Uncertain (1 — not posted unless approved)

**`AmplitudeProvider.tsx:201–203` — `{domain: undefined}` passed unconditionally; Amplitude SDK v2 behavior with explicit `undefined` vs. absent `cookieOptions` is unknown**  
When `cookieDomain` is absent from config but `apiKey` is present, `amplitude.init()` receives `cookieOptions: { domain: undefined }`. An explicit `undefined` means the key exists on the object (`'domain' in cookieOptions === true`). If the SDK checks key presence rather than truthiness, this would suppress default domain inference — exactly the bug this PR fixes. In practice all current environments with an `apiKey` now also have `cookieDomain`, so the exposure is limited to future environments added without the field. SDK internals not verifiable (node_modules not installed). Conditional spread (`...(cookieDomain ? { cookieOptions: { domain: cookieDomain } } : {})`) would be lower-risk.

### Nits (1)

**`AmplitudeProvider.test.tsx:858–859` — Test name implies value sourcing but only verifies key structure**  
`'passes cookieOptions.domain from appconfig to amplitude.init'` implies the value was read from appconfig. The test comment directly contradicts this: domain is `undefined` in tests. Consider renaming to `'uses cookieOptions.domain SDK option key (not legacy top-level cookieDomain)'` to accurately describe what is verified.

### False Positives Excluded
- `pilot.yaml` missing `cookieDomain`: pilot.yaml has no `amplitude` block at all (confirmed by reading the file). PR description is correct: "pilot.yaml / base.yaml have no amplitude block (no apiKey → SDK is never initialized), so no change needed there." Multiple agents fabricated an amplitude block that doesn't exist.
