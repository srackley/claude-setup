Adds `cookieOptions: { domain: appSettings?.config?.amplitude?.cookieDomain }` to `amplitude.init()` and adds per-env `cookieDomain` to `.config/dev.yaml` + `.config/prod.yaml`. ### VALID — Suggestion

**packages/wanderu-analytics/src/tests/AmplitudeProvider.test.tsx:862–871 — Test only verifies key presence, not value threading**

The new test uses:
```ts
expect(initOptions).toHaveProperty('cookieOptions');
expect(initOptions.cookieOptions).toHaveProperty('domain');
```

Jest's `toHaveProperty('domain')` passes even when `domain` is `undefined` (key present, value absent). The test environment config has no `cookieDomain` field, so `domain` is `undefined` in every assertion. The test would pass for a typo in the config path, wrong object reference, or hardcoded `undefined`. The PR's entire purpose is to wire `cookieDomain` from per-env config through to `amplitude.init()` — the test doesn't prove that wiring exists.

**Challenger verdict:** Confirmed.

**Recommended fix:** Add a second `it` block using the `setConfig` mock helper to inject a known `cookieDomain` value and assert it reaches `amplitude.init`:
```ts
it('threads the configured cookieDomain value to cookieOptions.domain', async () => {
  setConfig({ ...defaultConfig, config: { ...defaultConfig.config, amplitude: { ...defaultConfig.config.amplitude, cookieDomain: '.wanderu.com' } } });
  // render + flushEffects ...
  expect(initOptions.cookieOptions?.domain).toBe('.wanderu.com');
});
```

### UNCERTAIN (not posted without explicit approval)

**packages/wanderu-analytics/src/AmplitudeProvider.tsx:201–203 — `cookieOptions: { domain: undefined }` vs. omitting `cookieOptions` entirely**

Two review agents disagreed on SDK behavior for when `cookieDomain` is absent from config. If the SDK uses `'domain' in options` semantics (rather than a null-guard), passing `{ domain: undefined }` could silently degrade cookie scoping. A safer implementation: `...(cookieDomain && { cookieOptions: { domain: cookieDomain } })` — omits the key entirely when unconfigured.
