## wanderu/canopy#597 — build(deps-dev): bump the commitlint group across 1 directory with 2 updates

**URL:** https://github.com/wanderu/canopy/pull/597  
**Status:** NEEDS_REVIEW  
**Reviewed:** 2026-05-28

### Summary

Dependabot bump of `@commitlint/cli` and `@commitlint/config-conventional` from v20.5.3 to v21.0.1. This is a **major version bump** — v21 has two breaking changes: minimum Node.js raised to v22.12.0 (from v18), and new default output format (`feat!: show input from a new line`; `--legacy-output` flag added for backwards compatibility).

**Safety verdict:** Safe to merge. All breaking changes are handled:
- Node 24.3.0 (`.tool-versions`) satisfies the >=22.12.0 requirement
- The husky hook (`pnpm dlx commitlint --edit $1`) uses exit code not stdout, so the output format change has no effect
- `import-meta-resolve` was removed from `@commitlint/resolve-extends` and replaced by native `import.meta.resolve()` — fine on Node 24
- yargs v17→v18 requires Node `^20.19.0 || ^22.12.0 || >=23` — satisfied by Node 24

The parserPreset workaround in `commitlint.config.mjs` remains functionally correct under v21. `@commitlint/resolve-extends@21.0.1` still uses `es-toolkit mergeWith` (same semantics as before, just different library name than the comment claims).

### Blocking

None.

### Suggestions (1)

**`commitlint.config.mjs:22-23`** — Maintenance instruction should also trigger on @commitlint bumps

The comment says: "When bumping conventional-changelog-conventionalcommits, re-diff this object against the new createParserOpts() output."

This instruction is incomplete. A `@commitlint/resolve-extends` version bump can change the *merge engine* itself — in some v20.x versions, `lodash.mergewith` was used; in v21, it is `es-toolkit`. The type-mismatch assumption the workaround rests on ("user object wins when types mismatch") depends on the merge engine's behavior. If that behavior changes, the full-object approach could stop being necessary, or worse, stop working as expected.

**Suggested fix:**
```
// When bumping conventional-changelog-conventionalcommits, re-diff this object
// against the new createParserOpts() output.
// When bumping @commitlint/resolve-extends, re-verify the parserPreset
// type-mismatch merge behavior and update the "Verified at" line below.
```

Note: The v20→v21 merge engine change (lodash → es-toolkit) did not break the workaround in this case, but the comment gave no signal to check.

### Nits (3)

**Nit 1 — `commitlint.config.mjs:~17`** — Wrong library name in comment

The comment reads: "@commitlint/resolve-extends uses lodash.mergewith, which lets the user object win when types mismatch"

`@commitlint/resolve-extends@21.0.1` (and in fact @20.5.3 as well) depends on `es-toolkit: 1.46.1`, not `lodash.mergewith`. The `lodash.mergewith@4.6.2` entry in the lockfile belongs to the optional `@commitlint/resolve-extends@20.2.0` snapshot — not the version used by this project's commitlint toolchain.

**Fix:** Change "lodash.mergewith" → "es-toolkit mergeWith" in the comment.

---

The comment reads: "Verified at @commitlint/load@20.5.0."

`@commitlint/load@20.5.0` does not appear in the pnpm lockfile — the project was at `20.2.0` (via the optional chain) and now at `21.0.1`. The version referenced in the comment was never installed.

**Fix:** Update to "Verified at @commitlint/load@21.0.1."

---

**Nit 3 — `commitlint.config.mjs:~5`** — Stale transitive dep version in comment

The comment reads: "Copied from createParserOpts() in conventional-changelog-conventionalcommits@9.3.0"

The pnpm lockfile shows `conventional-changelog-conventionalcommits@9.3.1` as the installed version (both before and after this PR). The 9.3.0→9.3.1 bump happened in a prior dependabot PR that did not update this comment.

**Fix:** Update "@9.3.0" → "@9.3.1" and confirm createParserOpts() output is unchanged between those versions (the comment's own instruction applies here).
