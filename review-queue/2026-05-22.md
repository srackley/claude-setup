### SUGGESTIONS (1)

**S1 — `console.warn` once-per-module guard is completely untested**  
`packages/wanderu-ducks-trips/src/appstate/selectors.js:329–338`  
Challenger verdict: **Confirmed**

No test spies on `console.warn` or asserts the once-per-module guard fires and suppresses correctly. `jest.clearAllMocks()` in `beforeEach` does not reset the module-level `multiPaxPaxAwareBranchLoggedOnce` variable. If the `if (!multiPaxPaxAwareBranchLoggedOnce)` guard were inverted or removed, every existing test stays green. The PR description explicitly frames this warn as the production signal for detecting a silent 2× pricing regression after wapi deploys; leaving it untested means the safety net is invisible to the test suite.

Suggested addition (requires `jest.isolateModules` or an exported reset helper):
```js
it('emits console.warn on first pax-aware invocation', () => {
    jest.spyOn(console, 'warn').mockImplementation(() => {});
    selectTripPrices(state, 'trip-123', 2);
    expect(console.warn).toHaveBeenCalledWith(
        '[multi-pax-amt] pax-aware pricing branch fired',
        expect.objectContaining({ feature: 'multi-pax-amt-pax-aware' })
    );
});

it('suppresses console.warn on second pax-aware invocation', () => {
    jest.spyOn(console, 'warn').mockImplementation(() => {});
    selectTripPrices(state, 'trip-123', 2); // first — fires
    selectTripPrices(state, 'trip-123', 2); // second — suppressed
    expect(console.warn).toHaveBeenCalledTimes(1);
});
```

### DISPUTED (3 — not posted without explicit approval)

**D1 — `basePricing = [undefined]` can silently corrupt pricing accumulator**  
`selectors.js:340–344`  
Challenger verdict: **Weakened** (valid logic chain, requires wapi contract violation)

`getSingleTripPricing(null)` returns `[undefined]` (confirmed: `formatTripPricing(null)` → `undefined`, wrapped in `[]`). `[undefined]` is truthy and bypasses the `!basePricing && !lcPricing` guard. If `pricing_is_pax_aware: true` arrives with `pricing: null` (a wapi self-contradiction), the spread inserts `undefined` into both accumulator arrays silently. The existing `× seats` branch would crash on `Object.entries(undefined)` in the same scenario (fail louder). No defensive guard and no test covers this case. Weakened because the scenario requires a wapi bug, not a client-side error.

---

**D2 — Module-level flag survives across SSR requests (once-per-process, not once-per-page-load)**  
`selectors.js:45, 329–338`  
Challenger verdict: **Weakened** (DD RUM is browser-only; SSR concern doesn't impair stated observability purpose)

In SSR the module is loaded once per server process. After first pax-aware request, flag is permanently `true`. **However:** `@datadog/browser-rum` is initialized only in `client.jsx`, not `server.jsx`. SSR-side `console.warn` goes to server logs/APM, not DD RUM. The "once per page load" claim is accurate for the browser path where DD RUM operates. Residual risk: future developers expecting repeated SSR emissions would be confused.

**D3 — `selectTripPricingIsPaxAware` is a plain function, not `createAppSelector`**  
`baseTripSelectors.js:301–304`  
Challenger verdict: **Weakened** (plain functions are precedented; `selectTripPrices` itself is not memoized)

All other `createAppSelector` selectors in the file cache computationally meaningful derived data. This function does a trivial `=== true` check on an already-memoized `selectTripData` result. Its only call-site is inside `selectTripPrices` (itself not memoized), so memoizing here adds cache-miss overhead with no cache-hit benefit. Prior art: `selectTripInformation`, `selectForLeg`. Worth a code comment explaining the intentional choice.

### SUGGESTIONS (1)

**S1 — Test verifies key presence but not value; inline comment overstates sourcing guarantee**
`packages/wanderu-analytics/src/tests/AmplitudeProvider.test.tsx:866–871`
Challenger verdict: **Confirmed**

The new test in `describe('AmplitudeProvider cookieOptions.domain')` asserts:
```ts
expect(initOptions).toHaveProperty('cookieOptions');
expect(initOptions.cookieOptions).toHaveProperty('domain');
```
The test config (`explorer.config.local.js`) has no `cookieDomain` field, so `domain` is always `undefined`. `toHaveProperty('domain')` passes for `{ domain: undefined }`. The test cannot distinguish the correct config path (`appSettings.config.amplitude.cookieDomain`) from any other expression that produces `undefined` — a wrong-key read or accidental hardcode would pass identically.

The inline comment at lines 867–868 states "it sources from `appSettings.config.amplitude.cookieDomain` (per-env config)" — this is not verified by any assertion in the test.

Suggested fix: use `setConfig` (already exported from `__mocks__/wanderu-config.js`) to inject a known domain, then assert the actual value:
```ts
it('passes configured cookieDomain to amplitude.init cookieOptions.domain', async () => {
    setConfig({ config: { amplitude: { apiKey: '...', cookieDomain: '.wanderu.test' } } });
    // ... render ...
    expect(initOptions.cookieOptions?.domain).toBe('.wanderu.test');
    // restore config in afterEach
});
```
Also update the comment to accurately describe what the existing assertion proves (SDK key shape: `cookieOptions.domain` not legacy `cookieDomain`) vs. what it does not (value sourcing).
